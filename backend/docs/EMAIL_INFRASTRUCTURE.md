## 1. Architecture Overview

Deal One uses a dedicated, globally exported NestJS `EmailModule` (`src/modules/email/`) backed by the official **Resend Node.js SDK**:

- **`EmailService`**: Single centralized Resend client, sender configuration, 10s request timeout, exponential backoff retries (max 3 attempts for network errors, `429`, and `5xx`; never retries `4xx`), `Idempotency-Key` support, structured JSON logging with masked recipients.
- **`EmailVerificationService` & `EmailVerificationController`**: Secure single-use email verification tokens (256-bit random, SHA-256 hashed in Redis with configurable TTL, 60s resend cooldown, automatic invalidation of prior tokens, anti-enumeration).
- **Templates (`src/modules/email/templates/`)**: Table-based, responsive, zero-external-dependency HTML + plain-text templates supporting Arabic (`dir="rtl"`) and English (`dir="ltr"`) with strict HTML escaping (`escapeHtml`) on all user-supplied fields.
- **Event Integration**:
  - `AuthService`: Welcome email (on OTP registration when email is present), Security notifications (`PASSWORD_CHANGED`, `PASSWORD_RESET`, `ALL_SESSIONS_TERMINATED`).
  - `EmailVerificationService`: Verification link, Verification confirmation, and `EMAIL_CHANGED` security notification to previous verified email.
  - `ModerationService`: Listing approved & listing rejected (with reason code/notes) emails after `$transaction` commit.
  - `OutboxPublisherProcessor`: Payment receipt emails on verified `PAYMENT_SUCCEEDED` outbox events.

## 3. Domain Verification & DNS Records

Preferred production sending domain: **`mail.dealone.eg`** (subdomain isolates transactional reputation from the root domain).
Preferred sender: **`Deal One <noreply@mail.dealone.eg>`**.

Because DNS for `dealone.eg` is not accessible from this environment, **no DNS records have been invented or modified**. Follow these steps once you own/control the domain:

1. In Resend Dashboard → **Domains** → **Add Domain** → enter `mail.dealone.eg` (select region closest to Railway `iad` / `us-east-1` or `eu-west-1`).
2. Copy the **exact** DNS records generated by Resend and add them at your DNS provider:

| Record Purpose | DNS Type | Host / Name | Value | Notes |
|---|---|---|---|---|
| **DKIM** (signing) | `TXT` | `resend._domainkey.mail` (exact name from Resend) | Exact value from Resend Dashboard | Proves email authenticity |
| **SPF / Return-Path** | `MX` & `TXT` | `send.mail` (exact name from Resend) | Exact values from Resend Dashboard | Do not duplicate existing SPF records on the same host |
| **DMARC** (policy) | `TXT` | `_dmarc.mail` (or `_dmarc` on root) | `v=DMARC1; p=quarantine; pct=100; adkim=r; aspf=r;` | Start with `p=none` for monitoring, then tighten to `quarantine`/`reject` |

3. Click **Verify DNS Records** in Resend and confirm status reaches **Verified**.
4. Update `EMAIL_FROM` in Railway to `Deal One <noreply@mail.dealone.eg>`.

### Testing Sender Limitations (`onboarding@resend.dev`)
Until your domain is verified, `EMAIL_FROM` defaults to `Deal One <onboarding@resend.dev>`:
- Can **only** send to your own Resend account email address or Resend test addresses (`delivered@resend.dev`, `bounced@resend.dev`).
- Must **not** be used for general end-user production traffic.

## 6. Email Verification Flow

1. Authenticated user calls `POST /api/v1/auth/email/verification/request` (or `/resend`) with optional `{ "email": "user@example.com" }`.
2. Backend checks active user, enforces 60s Redis cooldown (`SET NX`) and route rate limit (`3 req / 15 min`).
3. If another user already owns that email, backend logs an audit event and returns the same generic `200 OK` response (anti-enumeration).
4. Any previous active token for that user is deleted from Redis.
5. Backend generates a 256-bit random token (`crypto.randomBytes(32).toString('base64url')`), stores **only** `SHA-256(token)` in Redis (`email:verify:token:<hash>`) with TTL, and emails `${APP_PUBLIC_URL}/verify-email?token=<rawToken>`.
6. Client/web link submits `POST /api/v1/auth/email/verify` with `{ "token": "..." }`.
7. Backend hashes token, looks up Redis, immediately deletes token (single-use / anti-replay), updates `User.email` and `User.isEmailVerified = true`, logs `EMAIL_VERIFIED` audit event, and sends confirmation (plus `EMAIL_CHANGED` alert to old verified email if changed).

## 10. Troubleshooting

- **`checks.email: "unconfigured"` in `/health/ready`**: `RESEND_API_KEY` is missing, empty, or matches a placeholder pattern. Set a valid key in Railway Variables and redeploy.
- **Resend `403` / `422` validation error**: Usually caused by sending from an unverified domain or sending from `onboarding@resend.dev` to an address other than the Resend account owner's email.
- **`429 Too Many Requests` on verification request**: 60-second per-user cooldown or `3 / 15 min` rate limit is active.

---

## 11. Security Considerations

- Zero hardcoded keys; `RESEND_API_KEY` is read strictly from `ConfigService`.
- Verification tokens are never stored in plaintext (SHA-256 hash only) and never logged.
- Recipient emails are masked in structured logs (`u***@example.com`).
- All user-supplied template values are escaped via `escapeHtml()`.
- Email verification never alters user roles or permissions.
- Email provider outages are isolated and never roll back auth, moderation, or payment transactions.

## 12. Flutter API Integration Contract

Base URL: `https://one-deal-cjjt-production.up.railway.app/api/v1`

### 1. Request Email Verification
- **Endpoint:** `POST /auth/email/verification/request`
- **Auth:** `Authorization: Bearer <accessToken>`
- **Rate Limit:** 3 requests / 15 minutes + 60s cooldown
- **Body:**
  ```json
  { "email": "user@example.com" }
  ```
  *(Optional if `user.email` is already set on profile)*
- **Response (`200 OK`):**
  ```json
  {
    "success": true,
    "data": {
      "success": true,
      "message": "If this email address is eligible, a verification link has been sent.",
      "expiresInMinutes": 30,
      "cooldownSeconds": 60
    }
  }
  ```

### 2. Resend Email Verification
- **Endpoint:** `POST /auth/email/verification/resend`
- **Auth:** `Authorization: Bearer <accessToken>`
- **Rate Limit:** 3 requests / 15 minutes + 60s cooldown
- **Body / Response:** Identical to `POST /auth/email/verification/request`. Invalidates any previously issued token.

### 3. Verify Email Token
- **Endpoint:** `POST /auth/email/verify`
- **Auth:** Public (no Bearer token required — works directly from email deep link)
- **Rate Limit:** 10 requests / 15 minutes
- **Body:**
  ```json
  { "token": "<token-from-verification-url>" }
  ```
- **Response (`200 OK`):**
  ```json
  {
    "success": true,
    "data": {
      "success": true,
      "message": "Email address verified successfully.",
      "isEmailVerified": true
    }
  }
  ```
- **Error (`400 Bad Request`):** Invalid, expired, superseded, or already consumed token.
